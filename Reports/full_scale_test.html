02Build

Turn a PDF into a corpus, with no network

5 minutes

$ export DSA_PARTS_DIR=/c/tmp/dsatest/parts
$ export DSA_CACHE_DIR=/c/tmp/dsatest/cache
$ .venv/Scripts/dsa.exe build lm741.pdf --part LM741 --vendor unknown
Observed · exit 0 40 sections · 6 tables · 3 figures · 10 footnotes · 71 spec records · 3 plot files. Corpus 13 672 tokens; INDEX.md 2 253 tokens against a 3 000 budget; page coverage 40/40.
Why --vendor unknown It is required to build a TI part offline. Without it, vendor detection pins ti, which routes to the ti_html backend and needs network — and that path crashes rather than degrading. See finding F2.
03Verify

Verify — and learn to read the number

5 minutes

$ .venv/Scripts/dsa.exe verify --part LM741 --pdf lm741.pdf
Observed 17/17 passed (100%)

Now run it without --pdf and watch the identical corpus report 2/17 passed (12%). Nothing is broken: the page-truth check is disabled, but a disabled check renders as ❌ and still counts in the headline.

Rule Always pass --pdf. For a part with companion documents it must point at the document the questions are actually sourced from — see stage 05 and finding F12.
04Retrieval

The surfaces a designer actually touches

15 minutes

$ dsa ask    --part LM741 "what is the maximum supply voltage?"
$ dsa search --part LM741 "offset null"
$ dsa card   --part LM741 --card power
$ dsa pins   --part LM741
$ dsa plots  --part AFE7950 --y-label "Fullscale"
  • ask → Supply voltage: ±22 V (max) — §6.1, p.4 [low], a supporting excerpt, and a Verify: Printed page 4 of lm741.pdf footer. Correct.
  • search → BM25 hits with scores and page cites.
  • card → provenance table with grades, plus the disambiguation note “largest of 2 printed values for this parameter”. Syntax is --card power, not a positional argument.
  • pins → an honest-degradation message. But LM741 does print a pin table and extraction yielded zero pins — finding F6.
  • plots → filters on the printed axis and states its blind spot: “23 of 514 figures publish no readable y axis … cannot establish that no such figure exists.” That sentence is the behaviour to look for everywhere.

Now try to make it lie

$ dsa query --part LM741 --symbol NOSUCHSYMBOL
$ dsa ask   --part LM741 "what is the gate charge?"
$ dsa regs  --part LM741

A good result is an explicit “not found, and here is what I looked for.” A bad result is a confident wrong number. Report anything that guesses.

07Phase 7/8

Revision awareness — does this corpus still match upstream?

20 min · verified live 2026-08-18

Landed and verified: tickets 01–04 — document registry and dsa fetch, revision awareness and staleness, dsa diff-rev, errata cross-linking. Still running: tickets 05–08 and all of Phase 8. Run git log --oneline first — a command whose ticket has not landed simply will not exist.

Every line below was observed against live TI, not copied from --help.

$ dsa check-revisions --all
STALE     LMX1204 (datasheet): upstream reports SNAS800B; this corpus is built from SYSREFOUT0
current   AFE7950 (datasheet): upstream reports SBASA41E, unchanged — but the bytes
          differ: the document was regenerated, not revised
unchecked AD9081 (datasheet): no registry URL for this datasheet — nothing to check
          against. Record one with `dsa fetch --url <URL> --part AD9081 --doc-type datasheet`
3 checked, 1 stale, 2 content-drift, 4 could not be checked      # exit 1

Three things to look at, because they are the point of the phase:

  1. Content drift is worded “regenerated, not revised.” TI re-stamps a dated package-materials page daily, so the sha256 churns on an unchanged document. A hash difference alone must never read as a new revision.
  2. unchecked is loud and prints the command that fixes it — it is not folded into a pass count.
  3. Exit is 1 when anything is stale, 0 when clean — usable as a gate.
Corpora built before f32d9a9 must be rebuilt That STALE LMX1204 line is not an outdated corpus. SYSREFOUT0 is a real pin name in the part, and the old doc-ID regex grabbed the first token that looked like a TI literature number anywhere in the text. The wrong value was baked into sources.json at build time, so the part reports STALE forever until rebuilt. Rebuild and re-check: current LMX1204 … unchanged, exit 0, content_drift false, and an upstream sha256 matching the local build byte for byte. Verified end to end.
Errata cross-linking is the one feature you cannot fully exercise today No real vendor errata PDF exists in this repo, so its gate used a real datasheet with synthetic errata prose. Two caveats the implementer recorded honestly: the errata banner is inserted into the section body, so an answer pack’s “Supporting excerpt” can quote errata prose under the datasheet’s page citation and displace the verbatim text it meant to support; and an erratum’s page is a range, not a point.

✓Scoring

What “pass” means

  • pytest green, ruff clean
  • All seven parts build and verify at 100% with the correct --pdf
  • Every answer you spot-check against the printed page is correct
  • Every question it cannot answer is declined, not guessed
  • MCP registers in your client and answers questions 1–4
  • Question 5 is declined

The system does not pass merely because the tests are green. The objective function is the golden Q&A set and your own spot-checks against printed pages. Green tests prove the machinery runs; only a page you opened yourself proves the answer is true.

If something fails

  1. Re-run with the exact command from this page — most surprises are F1 (missing --pdf) or F12 (wrong --pdf on a multi-document part).
  2. dsa status shows configuration, detected parts, and recorded reasons.
  3. KNOWN_SHORTCOMINGS.md records measured limits with the test that measures them — check there before filing something as new.
  4. For a build failure, re-run with --vendor unknown to force the offline pdf_layout floor and see whether it is a backend-routing problem.
