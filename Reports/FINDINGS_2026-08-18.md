## F1 — `dsa verify` renders a *disabled* check as a *failure* (HIGH)

Without `--pdf`, page-truth checking is disabled, but the disabled column
still prints ❌ and still counts in the headline:

- `dsa verify --part LM741` → `**2/17 passed (12%)**`
- `dsa verify --part LM741 --pdf lm741.pdf` → `**17/17 passed (100%)**`

Same corpus. The only warning is one dim line above the table
(`warning: --pdf not given; page-truth check disabled`).

**Why it matters:** this is the first command anyone runs to judge the system.
"12%" reads as catastrophic breakage when the corpus is perfect.

**Fix:** render a disabled check as `—`, exclude it from the denominator, and
state in the headline that page-truth was not checked.

## F2 — TI-routed build dies with a raw traceback when the viewer URL 404s (HIGH)

`dsa build lm741.pdf --part LM741TI` (vendor auto-detected as `ti`) →
uncaught `requests.exceptions.HTTPError: 404 Client Error ... /lit/gpn/LM741TI`,
full Python traceback, no fallback to `pdf_layout`, no actionable message.

**Why it matters:** invariant 7 (honest degradation) is not honored on the
acquisition path, and this is the exact path a 20-part fleet onboarding walks.
Any part whose TI document-viewer page is missing kills the run with a stack
trace.

**Fix:** catch it, report URL + status, and either fall back to the
`pdf_layout` floor with a recorded degradation or fail with a message naming
`--vendor unknown`.

## F3 — `dsa batch` has no `--vendor` override (MEDIUM-HIGH)

`dsa batch <dir>` auto-detects vendor per PDF with no way to force the offline
`pdf_layout` floor. Combined with F2, a directory containing any TI part whose
viewer page is missing cannot be batch-built offline at all.

## F4 — TI datasheet sha256 is not stable over time (HIGH — design impact)

Measured against live TI servers:

| Part | URL result | Revision | sha256 vs local |
|---|---|---|---|
| LM741 | 200 | SNOSC25D = SNOSC25D | **differs** |
| AFE7950 | 200 | SBASA41E = SBASA41E | **differs** |
| AFE7953 | 200 | unchanged | **differs** |
| LMX1204 | 200 | SNAS800B | **identical** |

Root cause, confirmed by page diffing: TI **regenerates the "PACKAGE MATERIALS
INFORMATION" addendum with the current date on every download**. LM741 printed
p.15 reads `10-Aug-2026` upstream vs `15-Jul-2025` locally.

AFE7950 additionally has **one extra local page** — a tray addendum at printed
p.139. Pages 1–138 align exactly; from p.139 on, local page N = upstream N−1.
Verified: `local[139] == upstream[138]`.

**Why it matters:** Phase 7 spec'd a hash mismatch as "a new upstream revision
is available". That would fire a false staleness alarm on every TI part every
day, training the user to ignore the one warning that protects a design
decision.

**Action taken:** amended `.scratch/reach-and-trust/issues/02-revision-
awareness.md` with the evidence table and two new criteria — staleness must be
decided by the **parsed revision identifier**, never by hash alone, and a hash
difference under an unchanged revision must be reported distinctly as content
drift. Added a shorter measured note to ticket 01.

## F6 — LM741 prints a pin table; extraction yields 0 pins with no reason (MEDIUM)

## F8 — `sniff_revision` returns a signal name for LMX1204 (HIGH)

```
sniff_revision('tests/fixtures/pdf/lmx1204.pdf')  ->  'SYSREFOUT0'
                                                       expected 'SNAS800B'
```

`extract/pdf_structure.py:78`:
`_TI_DOC_ID = re.compile(r"\bS[A-Z]{2}[A-Z0-9]*\d[A-Z0-9]*\b")` matches the
pin name `SYSREFOUT0`, and `sniff_revision` uses `.search()` — the first match.
Page-1 matches in order:
`['SYSREFOUT0','SYSREFOUT1','SYSREFOUT2','SYSREFOUT3','SNAS800B']`.

The other six documents parse correctly (LM741 `SNOSC25D`, AFE7950
`SBASA41E`, LMX1204 register map `SNAU269A`, AD9081 `Rev. 0`, HMC520A
`Rev. A`, QPA1003P `Rev. I`).

**Why it matters:** it corrupts the LMX1204 corpus's recorded revision, and it
directly undermines the revision-first staleness rule added to ticket 02 —
comparing `SYSREFOUT0` against an upstream revision is meaningless.

**Action taken:** added as a blocking prerequisite with the diagnosis and a
proposed shape to `.scratch/reach-and-trust/issues/02-revision-awareness.md`,
plus a regression criterion covering all seven documents.

## F11 — the alias ladder matches `TJ` too loosely (LOW-MED)

`dsa ask --part AFE7950 "what is the maximum junction temperature?"` returns
four cited rows, one of which is **`TJ Total Jitter Tolerance: 0.42 UI (max)`**
— a jitter spec surfacing in a thermal question because both resolve through
the symbol `TJ`. The three genuine rows also disagree (125 °C labelled `(min)`,
150 °C max, 110 °C max) without stating which condition applies.

Presenting all cited candidates rather than picking one is the right default;
the defect is that a clearly unrelated parameter is among them.

## MCP — outstanding item now largely resolved (POSITIVE)

Open across three previous runs. Driven as a **real subprocess over actual
stdio** (not the in-process `mcp.shared.memory` transport the existing tests
use, which cannot catch stdout pollution or entry-point breakage):

- `initialize` → correct capabilities + instructions block
- `tools/list` → **13 tools**: `list_parts`, `list_projects`, `get_index`,
  `search`, `find_spec`, `find_plots`, `find_pin`, `find_register`,
  `get_card`, `read_section`, `get_figure`, `compare_parts`, `ask`
- `tools/call ask` on AFE7950 → real cited answer, `tokens: 892` of a 6000
  budget, `truncated: false`, five citations

Two hypotheses tested and **disproved** (do not chase these):
- stdout pollution from the `fitz` deprecation warning — that warning goes to
  **stderr**; `dsa version` writes only `0.5.0` to stdout, so JSON-RPC framing
  is clean.
- double-encoded `§` in tool output — the raw bytes are `\xc2\xa7`, the
  correct UTF-8 for U+00A7. The mojibake was a cp1252 probe artifact.

Still genuinely unverified: registration through a GUI client's own UI. The
config block for that is in the runbook.

## F12 — `verify --pdf` takes ONE pdf, so companion-sourced goldens falsely fail (HIGH)

LMX1204 has two documents: the datasheet and `LMX1204_registermap.pdf`
(companion, registered with `dsa add-doc --type register_map`). All twelve of
its golden questions are sourced from the **companion**.

```
verify --part LMX1204 --pdf tests/fixtures/pdf/lmx1204.pdf            ->  2/12 (17%)
verify --part LMX1204 --pdf tests/fixtures/pdf/LMX1204_registermap.pdf -> 12/12 (100%)
```

Same corpus, same goldens, different `--pdf`. Proven not to be wording drift:
both expected strings for `q03` are present verbatim, exactly once, in the
exact section file verify reported checking —
`docs/register_map-0e7de32d/sections/1-lmx1204-registers.md` reads *"...
undocumented addresses and can be considered reserved. Writing to undocumented
addresses can prevent the device from working as intended."*

The section check passes; the **page-truth** check fails because it looks for
companion text on a page of the datasheet.

**Fix:** resolve each record's source PDF from `sources.json` (the corpus
already records it) instead of taking one global `--pdf`. Accepting repeated
`--pdf` would also work but pushes the bookkeeping onto the user.

**Combined with F1**, the `verify` headline is untrustworthy in two independent
ways: a disabled check renders as a failure, and a multi-document part is
scored against the wrong file.
